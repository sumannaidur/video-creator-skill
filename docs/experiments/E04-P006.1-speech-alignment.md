## Native timing

The hash-verified FP32 ONNX session has inputs `input_ids`, `style`, `speed` and outputs `waveform`, `duration`. Installed Kokoro ONNX 0.6.1 returned 125 timed phoneme entries for A and 156 for B using `create_timed`. The export describes duration frames of 600 samples at 24 kHz (25 ms nominal). The installed runtime maps cumulative token durations proportionally to the actual waveform length, adjusts for token padding and batch offsets, and adjusts for inserted pauses. The entries refer to retained phoneme-vocabulary symbols, including separators where applicable. The API supplies no native original-text word mapping, sentence timestamps, confidence or independent acoustic alignment. The original `create` calls discarded the timing sidecar. [Export implementation](https://github.com/thewh1teagle/kokoro-onnx/blob/main/scripts/export.py) · [Release description](https://github.com/thewh1teagle/kokoro-onnx/releases/tag/model-files-v1.1)

The replay of A contained 183,960 frames versus the original 178,200. B had the original 214,200 frames but different PCM bytes. Neither replay attested to the timing of the original. Replay timing is retained only in the evidence JSONs. The canonical timelines contain measured waveform intervals and leave sentence, phrase and word times unknown. No subtitles were exported.

## P006.2A — capture during synthesis

Both new Hindi WAVs were generated in one ONNX graph call per passage with Kokoro ONNX 0.6.1 and ONNX Runtime 1.32.0. The [capture script](../../experiments/E04/native-timing/capture_native_timing.py) verified the model and voice-bundle hashes, checked the original text against the fixture, recorded actual phonemizer output and graph inputs and outputs, and linked the WAV hash and timeline with a unique run ID. Raw float32 waveforms are retained as NumPy arrays. Each PCM16 WAV was written directly with SoundFile, without normalization or resampling. Both decoded fully in FFmpeg and had nonzero audio and zero PCM samples at the clipping rails. Neither new WAV hash matches its corresponding E03 recording. Byte-for-byte reproducibility was not established.

| Passage | Waveform float32 shape | Duration int64 shape | Frames × 600 | Start/end special token frames | Timed symbols | Untimed text spans | Peak sampled tree / minimum available RAM |
| --- | --- | --- | --- | --- | ---: | ---: | --- |
| A | `[178200]` | `[127]` | 297 × 600 = 178,200 (7.425 s) | 23 / 1 | 125 | 20 | 555.8 MiB / 4.439 GiB |
| B | `[214200]` | `[158]` | 357 × 600 = 214,200 (8.925 s) | 22 / 1 | 156 | 23 | 581.6 MiB / 4.400 GiB |

One int64 duration entry corresponds to each token in the input row `[0, …, 0]`. The two zeros are leading and trailing special tokens. Their frame counts contribute to the waveform, and their intervals are excluded from the phoneme records. The fixed hop is 600 samples (25 ms at 24 kHz). Cumulative frame counts multiplied by this hop matched every returned runtime edge in these captures. The runtime normally scales its edges by the ratio of its raw sample count to its total predicted frames. The prototype requires exact 600-sample agreement and refuses to publish converted offsets if that assumption fails.

The runtime passes speed as a float tensor to the model. Both captures use 1.0. Other speeds were not measured. Trimming, continuous mode and sentence/clause pause insertion were disabled, giving one batch at offset zero and exact equality between the flattened graph waveform and runtime audio. The standard noncontinuous path can split after punctuation or whitespace, add per-batch offsets, shift edges when trimming, and insert pause samples near punctuated marks based on quiet RMS frames. Those settings need their own conversion evidence. The original E03 default pause settings were not copied for this isolation test.

The installed frontend strips surrounding text whitespace, passes Hindi text to eSpeak NG with punctuation preservation and stress enabled, filters by the model vocabulary and collapses phoneme whitespace before batching. Its output is a symbol sequence, with punctuation, spaces, length markers, and combining marks as possible entries. The runtime exposes no grapheme spans. Indic conjuncts and matras can affect multiple output symbols, and several written code points can shape a single spoken unit. The two captured inputs do not test numeral expansion or embedded English. Those cases remain unverified, and the single Hindi phonemizer call supplies no separate code-switch mapping. Some dots in A and B occur inside phonetic strings, and the display danda is absent from the retained strings. Exact original-word, phrase, caption and animation timing coverage is zero. The 43 unknown text spans are whitespace-based review anchors for these Hindi fixtures.

## P006.2B — contextual Hindi text mapping

The installed Kokoro ONNX 0.6.1 tokenizer configures the packaged eSpeak NG library via espeakng-loader 0.2.4. Phonemizer 3.6.0 can mark backend word separators explicitly, preserve a configured punctuation set and warn or remove when word counts mismatch. Its interface returns strings rather than original-text offsets. Kokoro strips surrounding whitespace, uses default space separators, filters non-vocabulary symbols and collapses whitespace before batching. This removes distinct boundary metadata while retaining admitted space and punctuation tokens. The two NFC source strings were preserved verbatim. [Phonemizer API](https://bootphon.github.io/phonemizer/api_reference.html)

For both clips, restoring the marked separators to model spaces reproduced the complete captured symbol sequence and actual model token IDs exactly. The backend returned 20 and 23 groups, matching the ordered Hindi script spans. A had a repeated group on two spans, disambiguated for this prototype by group order plus corroborating isolated and prefix evidence. B had no repeated group. There were no unresolved or unmatched script spans under this gate. This verified correspondence for the two fixtures and does not imply that equal counts alone establish reliable mapping in other inputs.

Isolated-word phonemization introduced one extra primary stress marker in `में` in each sample. Contextual prefixes agreed exactly for 19/20 and 22/23 boundaries. The prefix ending at `में` showed the same stress difference. All prefixes agreed when compared without stress markers. Standalone phonemization matched the full-context symbol subsequences for all five editorial phrases. Sequence comparison found one deletion of a stress marker from isolated to contextual output per clip, with no insertions or substitutions. That diagnostic did not assign timing. Mapping retains the actual contextual stress tokens and excludes separator spaces and attached source question-mark/comma tokens from word endpoints. It preserves dots inside phonetic output and does not infer timestamps from danda, silence, or character counts.

## P013.2A.3 multi-segment narration

[`combine_segments.py`](../../experiments/E04/native-timing/combine_segments.py) combines synchronized WAV + candidate timeline pairs, in the order given (`ID=timeline.json`). It uses only the standard library and the existing `timeline.validate`.

- **Input checks:** each input is run through `validate`, which checks the WAV SHA-256, mono PCM16, and sample rate and count. All segments must share the same sample rate and locale.
- **Audio:** PCM frames are concatenated as-is, with no resampling. Silence of a whole number of samples goes at each boundary: `--gap-ms` or `--gap-samples`, either one value or a comma-separated value per boundary. A gap that is not a whole number of samples is rejected.
- **Records:** every record start and end is offset by an integer number of samples. Text references are offset into the combined text (segments joined by one space). Each record keeps a `segment` ID. Mapping internals stay segment-relative and are marked `mapping_scope: segment`. Each inserted gap is a `pause` record with label `inserted silence` and source `manual`.
- **Provenance:** a top-level `segments` list keeps each segment's ID, run ID, review status, source timeline path and SHA-256, source audio block, offset, sample count, text offset and the gap after it. The new `run_id` is derived from the segment run IDs, the audio hashes and the gaps. The status stays `unreviewed` unless every segment is reviewed.
- **Safety:** existing output files are never overwritten. After writing, an independent check confirms the total sample count, the audio hash, byte-exact segment audio, silent gaps, exactly offset records, records inside their own segment, and the preserved status.
